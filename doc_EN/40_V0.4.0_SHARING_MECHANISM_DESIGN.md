# V0.4.0 Sharing Mechanism Design

Status: design baseline for v0.4.0 sharing completion.

## 1. Goal

Sharing is a recoverable content-delivery flow, not a single navigation button. The user completes a rating and card first, chooses a target, and the product persists a recoverable draft before invoking any platform capability. Success, acceptance, cancellation, denial, failure, and unknown outcomes must remain distinct.

This release handles user-initiated sharing only. It does not upload in the background, publish on the user's behalf, read platform account data, or add a cloud relay.

## 2. User-visible targets

| Target | Input | Output | Leaves page? | Recovery |
| --- | --- | --- | --- | --- |
| Export PNG | Current card, ratio, theme | Local PNG | No | Keep editor state and retry |
| Save album | PNG data URI | System album image | Maybe | Classify cancel/denial/failure |
| System share | PNG/text through adapter | Native share sheet | Maybe | Restore page and draft on return |
| Xiaohongshu handoff | Confirmed title, body, tags, card image | Native posting flow | Yes | Accepted/cancelled/failed; never claim public posting |
| Toy/other container | Container-approved local handoff | Native flow | Container-defined | Use the same result categories |

An unsupported target must explain that it is unavailable without disabling local editing, preview, or export.

### 2.1 Target matrix and capability tiers

The product may keep these destinations as goals, but a platform without an approved container API must not be presented as direct publishing. The current tiers are:

| Container | Desired targets | What can be guaranteed now | Rebuttal / fallback |
| --- | --- | --- | --- |
| Bili Toy | QQ Zone, Bilibili Dynamic, WeChat, Tieba, Zhihu | PNG export, text/link copy, and the system share sheet; add a Dynamic entry only when Toy provides an explicit supported entry | The current Toy CLI/container has no unified posting API for these third-party platforms. `public`, `link-only`, or Toy publication does not mean that QQ/WeChat/Tieba/Zhihu were updated. Fall back to system share or manual paste |
| Xiaohongshu MiniTool | Xiaohongshu, QQ Zone, Bilibili Dynamic, WeChat, Weibo | Enter native Xiaohongshu posting only when the Bridge exposes `postNote` and the capability probe passes; use system share, copied text, or exported PNG for the rest | The current MiniTool Bridge exposes narrow Xiaohongshu post, temp-file, album, and open-app capabilities, not direct QQ Zone, Bilibili Dynamic, WeChat, or Weibo APIs. Never fake a “published” result |
| Desktop/Web | The same platform set | PNG file, copied text/link, and browser/OS share when available | Installation and prefill behavior are controlled by the OS/client; keep the local PNG and draft on failure |

The implementation order is fixed: album save (hard baseline) → local PNG export → system share sheet → platform-specific Bridge → public-status confirmation. An unavailable later tier must never remove an earlier local tier.

### 2.2 Permanent baseline: save the image to the album

Saving the final rating-card PNG to the system album is the minimum capability for every release and every container; it is not replaced by direct platform publishing. The album action uses the same PNG as the final preview, is user initiated, and distinguishes completed, cancelled, permission-denied, and write-failed outcomes. A successful album save only means that the image was saved; it never means that a platform post became public.

### 2.3 Optional personal signature

The confirmation page provides `Personal signature (optional)`:

- The user supplies a short text. When empty, it is omitted entirely, consumes no card layout space, and has no scoring effect.
- It may appear in the card footer and share text; preview, PNG, album output, and platform handoff use the same confirmed value.
- Adapters must not append account names, promotional topics, locations, watermarks, or platform copy.
- Clearing the draft or regenerating a card follows the user's confirmed local-draft policy for this field.

## 3. Standard flow

1. Edit metadata, axes, scores, and copy.
2. Choose ratio, theme, and optional reason/story visibility.
3. Render the official card; preview and export consume the same render input.
4. Choose export, album, system share, or platform handoff.
5. Persist the rating draft, card options, and pending-share summary before leaving the page.
6. For external handoffs, show a confirmation page and require an explicit final action.
7. On return, restore the editor, confirmation fields, and PNG; allow edit or retry.

## 4. Contract

```ts
interface ShareRequest {
  requestId: string;
  createdAt: string;
  source: 'desktop' | 'web' | 'minitool' | 'toy' | 'wechat';
  card: {
    ratio: CardRatio;
    theme: CardTheme;
    pngDataUri: string;
    width: number;
    height: number;
    algorithm: 'music-linear-100-v4';
  };
  text?: { title?: string; content?: string; tags?: string; personalSignature?: string };
  target:
    | 'file'
    | 'album'
    | 'system-share'
    | 'xiaohongshu-post'
    | 'bilibili-dynamic'
    | 'qq-zone'
    | 'wechat-share'
    | 'tieba'
    | 'zhihu'
    | 'weibo';
}

type ShareResult =
  | { status: 'completed'; requestId: string }
  | { status: 'accepted'; requestId: string }
  | { status: 'cancelled'; requestId: string; recoverable: true }
  | { status: 'denied'; requestId: string; recoverable: true; reason: string }
  | { status: 'failed'; requestId: string; recoverable: true; reason: string }
  | { status: 'unavailable'; requestId: string; recoverable: true; reason: string }
  | { status: 'unknown'; requestId: string; recoverable: true; reason: string };
```

PNG values must be complete `data:image/png;base64,...` URIs and dimensions must come from the final render. Text comes only from the user's confirmation fields; adapters may not append marketing copy, tags, locations, or mentions.

`accepted` means that a native platform accepted the handoff. Only `completed` means a local export/album operation completed. No platform handoff may be labelled “published” or “public”.

## 5. State machine

```text
idle → preparing → ready → confirming
                         ├─ cancel → cancelled → ready
                         └─ submit → persisting
                                      ├─ save-failed → failed
                                      └─ saved → invoking
                                                  ├─ completed
                                                  ├─ accepted
                                                  ├─ cancelled
                                                  ├─ denied
                                                  ├─ failed
                                                  └─ unavailable/unknown
```

Every recoverable terminal state keeps the rating draft, PNG, ratio, theme, confirmation text, and failure reason. A retry gets a new `requestId`; adapters never loop silently.

## 6. Adapter boundaries

| Layer | Owns | Must not own |
| --- | --- | --- |
| Domain core | Scoring and domain data | Platform calls or permissions |
| Card renderer | Deterministic preview/PNG | Accounts or share sheets |
| Share orchestrator | Validation, persistence, state machine, classification | Platform-private parameter assembly |
| Desktop adapter | Files, system share, window recovery | Scoring rules |
| MiniTool adapter | `writeTempFile`, album, approved Bridge | Network, background publishing |
| Bili Toy adapter | Toy-approved local interaction | Xiaohongshu Bridge or Bilibili cloud |
| WeChat adapter (1.1.0) | WeChat files, album, share, lifecycle | Domain defaults or scoring |

Capability probes are independent. Album support does not imply post support, and system-share support does not imply public publication.

## 7. Privacy boundary

- Metadata, scores, text, and cover stay in the local container while editing.
- Before an external handoff, explain what text/images go to which platform and who performs the final public action.
- Do not store account cookies, platform tokens, post IDs, or undeclared device identifiers.
- PNG rendering uses local resources only; no remote fonts, images, or analytics.
- Cancellation, denial, and failure do not delete data; the user can edit or retry.
- Clear actions remove pending-share data together with the local draft.

## 8. Failure taxonomy

| Status | Example | User action |
| --- | --- | --- |
| `invalid` | Invalid image, over-limit text, missing card | Return and fix |
| `unavailable` | Container lacks the capability | Use PNG/album |
| `cancelled` | Native sheet/page closed | Continue or retry |
| `denied` | Permission denied | Grant permission or export locally |
| `failed` | File, Bridge, or platform error | Review and retry |
| `unknown` | Page left or callback missing | Restore draft; never auto-submit again |

## 9. Acceptance matrix

- All 11 ratios use the same image for preview, PNG, album, and handoff.
- Character limits are visible before confirmation; Unicode truncation is code-point safe.
- Persist before invocation; cancel, denial, failure, return, and refresh restore content.
- Without a Bridge, editing, preview, and PNG generation remain usable and no fake success is shown.
- Build artifacts contain no external resources, network calls, arbitrary downloads, account reads, or hidden publishing.
- Keyboard/touch targets are at least 44px, statuses are readable, and focus returns to the initiating control.
- Desktop, MiniTool, and Toy have separate platform gates; WeChat is a 1.1.0 gate.

## 10. Handoffs

See the [V0.4.0 Sharing Mechanism Implementation Plan](./41_V0.4.0_SHARING_MECHANISM_IMPLEMENTATION_PLAN.md) for implementation order, code gaps, and acceptance cases.

- v1.1.0 adds only a WeChat adapter and its gates.
- v2.0.0 reuses the contracts in the standalone App instead of duplicating sharing or scoring logic.
