# V0.4.0 Standalone Mobile App and Multi-Domain Core Validation Plan

Status: Planned; formal implementation starts after the v0.3.1 M4 device gates close

Date: 2026-09-07

## 1. Product position

v0.4.0 is a standalone mobile-app validation release. It is neither a mobile extension of the Xiaohongshu MiniTool nor an early release of the 1.0.0 multi-domain product. It uses the existing music-rating flow to validate the mobile product form while progressively turning music-only implementation details into a reusable rating core for anime, books, film and television, and other domains.

Success in v0.4.0 does not mean adding as many domains as possible. It means proving the mobile foundations work reliably on real phones without duplicating scoring, archive, and card code for each future domain.

## 2. Objectives

- Deliver an installable, offline-capable standalone mobile-app candidate with real-device Android and iOS evidence.
- Reuse `music-linear-100-v4`, Archive Schema v2, and the production rating card without weakening existing data compatibility.
- Validate safe areas, soft keyboards, touch, rotation, background recovery, system sharing, image selection, and album save.
- Establish a platform-independent domain-definition model so axes, default templates, work fields, copy, and card labels can be configured by domain packs.
- Keep music as the public interaction while using anime, books, and film/television as internal contract fixtures proving the core has no music-only hard-coding.
- Produce the boundaries, migration decision, and real-device evidence needed to freeze the 1.0.0 multi-domain rater.

## 3. Out of scope for v0.4.0

- No public promise of complete anime, book, or film/television product experiences.
- No account, cloud sync, backend, telemetry, or online asset catalog.
- No Xiaohongshu `window.xhs.miniTool`, offline-ZIP, or `postNote` constraint inside the standalone app.
- No rewrite of existing React/TypeScript domain logic without necessity evidence.
- No freeze of the final 1.0.0 domain list, per-domain axes, or brand treatment.

## 4. Technical path and decision gate

Tauri Mobile is the preferred native-app-shell validation path, while the responsive PWA is the comparison baseline for reuse, performance, and accessibility. M0 must compare installation, offline behavior, file/media access, sharing, lifecycle, package size, and accessibility through minimum probes before freezing the v0.4.0 delivery shell.

Evaluate Flutter only when reproducible evidence shows that an essential plugin is unavailable, performance or screen-reader behavior fails, or required system interaction cannot be implemented reliably. A Flutter evaluation must include dual-stack maintenance cost, Archive compatibility, algorithm-parity tests, and a migration plan; “more native” is not sufficient justification.

Proposed platform boundary:

```text
Rating domain core
  ├─ DomainDefinition / preset packs
  ├─ scoring + archive migration + card view model
  └─ PlatformServices
       ├─ Web
       ├─ Windows desktop
       ├─ Xiaohongshu MiniTool
       └─ Standalone mobile App
```

Domain packs may supply declarative configuration and validated rules only; they must never call mobile, desktop, or MiniTool APIs directly.

## 7. Dependency order and parallel boundary

```text
v0.3.1 M4 device closure
  └─ M0-01 / M0-02 / M0-03 (parallel)
       └─ M0-04 shell ADR
            ├─ M1 mobile vertical loop
            └─ M3-01 domain-contract design
                 └─ M2 native media/data + M3-02–05 core validation
                      └─ M4 device candidate and 1.0.0 handoff
```

- Do not broadly add mobile plugins or change the production domain model before M0-04 passes.
- M1 and M3-01 may proceed in parallel after the boundary freeze, but M3 must not alter music behavior to accommodate internal fixtures.
- M2 system capabilities enter only through `PlatformServices`; permission implementations cannot bypass the domain boundary.
- M4 accepts only an exact candidate from a clean commit. Any content change increments the candidate and reruns the affected matrix.

## 8. Minimum multi-domain core contract

The domain definition validated, but not necessarily exposed publicly, in v0.4.0 includes:

- stable `domainId`, localized name, and version;
- default positive items, optional deduction rules, and weight constraints;
- configurable work fields such as artist, author, director, publisher, and release year;
- source distinction between domain defaults and user templates;
- card brand title, field order, and accessible description;
- domain identity, definition version, and migration entry in archives;
- safe fallback for unknown domains, missing domain packs, and old archives.

Identical input must produce matching results in shared algorithm tests across Web, desktop, MiniTool, and mobile. If a future domain needs another score range or aggregate rule, it must enter through versioned rule configuration rather than UI hard-coding.

## 9. Real-device matrix

Minimum acceptance includes:

- one older Android device still inside the chosen support window;
- one current Android device;
- one device on the current major iOS release;
- TalkBack and VoiceOver;
- portrait, landscape, keyboard, foreground/background, low storage, and permission denial/recovery;
- first launch and normal use without network access;
- Chinese, English, and long-text rating cards;
- import of an existing Archive and export/re-import from the app.

M0 probe evidence must determine exact minimum OS versions; public compatibility claims cannot precede device evidence.

## 10. Deliverables toward 1.0.0

At completion, v0.4.0 must leave 1.0.0 with:

1. a validated standalone mobile-app shell and platform-service contract;
2. domain-definition and scoring interfaces shared by at least four domain fixtures;
3. an Archive Schema v2 compatibility verdict and a written decision on whether Schema v3 is needed;
4. lossless music-archive migration and cross-platform algorithm-parity tests;
5. research checklists for anime, books, and film/television instead of unvalidated default axes;
6. Android/iOS performance, accessibility, permission, and failure-recovery baselines;
7. a 1.0.0 product-scope, domain-list, and migration-risk checklist.

## 11. Preliminary 1.0.0 position

1.0.0 is the `XDRate` multi-domain rater. Initial candidate domains include music, anime, books, and film/television; every additional domain requires separate research and product confirmation. Users select a domain, apply its presets or create a custom rating structure, and generate domain-specific cards under one product family.

Before 1.0.0 implementation, separate decisions must freeze the launch domains, default axes and deduction semantics, relationship between the flagship and vertical editions, package identities and upgrade paths, whether Schema v3 is required, and which of Web, desktop, and mobile are launch platforms.

## 12. Version, branch, and candidate policy

- Formal implementation uses short-lived `codex/v0.4.0-*` feature branches. Experimental dependencies must not enter the production build before the M0 probe is merged.
- One version-consistency gate keeps the package version, Tauri/mobile manifests, and user-facing identity aligned.
- M0/M1 artifacts are development probes or `alpha` builds only and must not be called mobile release candidates.
- Generate `0.4.0-beta.1` only after M2/M3 merge and data-migration gates pass.
- Generate `0.4.0-rc.1` after M4 automation, signing, and the exact-device matrix are ready. Package changes use `rc.2` or later and never overwrite old candidates.
- v0.4.0 neither changes existing v0.3.0/v0.3.1 MiniTool packages nor reuses their application identity, Bridge, or candidate hashes.

## 13. Primary risks and fallback

| Risk                                            | Early signal                                              | Response and fallback                                                                                                                         |
| ----------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Missing iOS build/signing device                | M0 cannot install on a real iPhone                        | Android probing may continue, but do not lower the iOS release gate; freeze platform scope only after macOS/Xcode/account access is available |
| Native plugin is overprivileged or unmaintained | It requests arbitrary files/network or has no maintenance | Build a narrow adapter, select a smaller-capability plugin, or fall back to PWA; schedule pressure never justifies broad permission           |
| Large-image memory peak or crash                | An older device exits on a high-resolution image          | Downsample, compress in stages, bound input, provide recovery, and gate peak memory on devices                                                |
| Multi-domain extraction changes music output    | Existing golden fixtures, PNGs, or archives change        | Block the merge; add a compatibility layer first, then use an explicit ADR and migration for necessary changes                                |
| Premature Schema v3 scope expansion             | Migration work grows before M3                            | Retain v2 by default; start a v3 decision only if domain identity cannot remain backward-compatible                                           |
| Mobile UI contaminates desktop code             | Platform conditions spread through domain components      | Tighten platform contracts and dependency checks; split entries when needed without copying domain logic                                      |

## 14. Estimate and release gates

Assuming toolchains and test devices are available, engineering is estimated at 25–40 effective development days: M0 4–7, M1 6–9, M2 5–8, M3 6–10, and M4 4–6. This excludes Apple/Google account review, certificate purchase, external store-review wait, and device procurement.

v0.4.0 may be released only when all conditions hold:

- M0–M4 atomic work packages are closed and bilingual docs, changelog, and user guidance are synchronized;
- exact Android/iOS candidates pass portrait/landscape, permission, lifecycle, and screen-reader matrices;
- existing music algorithm, Archive, and rating-card compatibility gates pass;
- internal anime, book, and film/TV fixtures prove the shared core without being advertised as finished products;
- offline, least-permission, signing, hash, and supply-chain gates pass;
- the 1.0.0 handoff review records every remaining research and decision item.
