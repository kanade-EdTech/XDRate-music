Automation proves the following scope:

- the ZIP root contains exactly one `index.html`;
- the React entry is an external classic IIFE script with `defer` in the document head;
- HTML, CSS, and JavaScript use only packaged relative resources;

## 5. Findings and resolutions

1. Vite emits a module entry by default, which violates the container contract. The MiniTool build emits a classic IIFE and audits final HTML rather than source only.
2. A classic script in the document head runs before the root node unless it has `defer`. E2E exposed this issue, and the build now forces `defer`.
3. React 19 reads `navigator.connection` to estimate preload speed. The MiniTool build replaces that runtime probe with the no-capability path to avoid a blocked device API.
4. React Scheduler uses an in-page `MessageChannel`. The audit forbids custom native protocols through `window`, `parent`, or `top` `postMessage`, while allowing standard same-page MessagePort scheduling.
5. The React production runtime originally carried a `react.dev` error-help URL string. It did not initiate a request, but the build now replaces it with a local error marker to avoid platform string-scan false positives. The auditor treats every non-W3C DOM-namespace URL string as a hard error.
6. The general ESLint task initially scanned generated output. `dist-minitool/` and `artifacts/` are now ignored while all source remains covered.

One Android Xiaohongshu real-host screenshot was received on 2026-09-05. It proves that:

- the MiniTool ZIP starts inside a page with Xiaohongshu host back/share controls;
- the first-screen React content renders, with no overlap or clipping across the heading, description, form, buttons, and status panel;

A single screenshot does not prove file selection, PNG generation, actual bridge invocation, album permission outcome, draft restoration after reopening, Android 8.1/WebView 61 compatibility, or screen-reader behavior. The device, OS, Xiaohongshu, and WebView versions were not supplied and remain “unrecorded.”

A subsequent 1080×1350 4:5 PNG output provides further evidence that:

- the Canvas 2D → PNG path succeeds in the Android Xiaohongshu host;
- physical output dimensions match the probe definition and the canvas boundary is complete;
- the Chinese title and description, English algorithm version, 80.0 aggregate, and `/ 100` all render correctly;
- there is no visible text overlap, edge clipping, mojibake, transparent background, or layout displacement.

The output alone cannot distinguish an in-page PNG preview from a file written to the system album through JSBridge. It therefore closes PNG generation only, not real `writeTempFile` → `saveImageToPhotosAlbum` invocation or permission acceptance.
