# V0.4.0 Sharing Mechanism Implementation Plan

Status: M0, M1, M2, and M3 complete; the M4 candidate package is built, while real-device and cross-container acceptance remain pending. This plan follows the V0.4.0 sharing design and closes the gaps between the design and current code.

## 1. Goal

Turn sharing into a recoverable engineering flow. After the user edits content, preview, PNG, album output, and platform handoff must reference one traceable card snapshot. External calls must persist the confirmed content first. Return, cancellation, denial, failure, and refresh must preserve content and avoid unexplained duplicate submissions.

Targets remain capability based: album save and local PNG are baseline capabilities, system share is a general capability, and platform Bridges are enabled only after probing. Platforms without an approved API stay outside direct publishing.

## 2. Current gaps

| ID  | Gap                                                                                                             | Evidence                                                                      | Risk                                                           |
| --- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| G1  | Editing score, copy, cover, or clearing content after preview does not invalidate the old PNG                   | `src/minitool/main.tsx` `generatePreview`, `saveAlbum`, `clearDefaultContent` | The user sees new content while saving or posting the old card |
| G2  | Confirmation edits live only in React state until final submit                                                  | `updatePostText` and `savePendingPostDraft`                                   | Crash or refresh loses the confirmed post text                 |
| G3  | Pending post data remains recoverable after `accepted`                                                          | `initialState` and `postNoteStorage.ts`                                       | Refresh can lead to duplicate submission                       |
| G4  | Missing Bridge, permission denial, temp-file failure, and album-write failure are not distinct enough in the UI | `minitoolBridge.ts` and album state                                           | Users cannot choose the right recovery action                  |
| G5  | Desktop/Web mainly provide file download; there is no shared system-share orchestrator                          | `browserPlatform.ts`, `desktopPlatform.ts`                                    | The ShareRequest design has no complete implementation path    |
| G6  | Optional personal signature exists in the design but not in draft, card, or post data                           | Domain types, Canvas, MiniTool form                                           | A documented feature cannot be delivered                       |
| G7  | Desktop export cancellation has no explicit result message                                                      | `RatingEditor.tsx` `exportCard`                                               | Users cannot tell whether saving completed                     |
| G8  | No direct preview versus final-output consistency gate                                                          | DOM card renderer and MiniTool Canvas renderer                                | Small layout differences can escape the 11-ratio matrix        |

## 3. Release boundary

### Required

- Snapshot invalidation and regeneration.
- Pre-call persistence, confirmation recovery, and idempotent handling after acceptance.
- Result classification for album save, export, system share, and the Xiaohongshu Bridge.
- `Personal signature (optional)` with identical preview, PNG, album, and handoff values.
- Acceptance for all 11 ratios, edit-then-export, refresh recovery, and duplicate-submit protection.

### Not promised in this release

- Direct publishing to QQ Zone, Bilibili Dynamic, WeChat, Tieba, Zhihu, or Weibo without an approved API.
- Reading public status, post IDs, or third-party account sessions.
- Background retries, cloud relays, or social-platform synchronization.

## 4. Implementation stages

### M0: Card snapshot and invalidation

1. Generate a stable `renderRevision` or content fingerprint from rating content, ratio, theme, cover, and signature.
2. Store preview as `{ dataUri, renderRevision, ratio, generatedAt }`; all edits, cover changes, ratio changes, and clear actions mark the old snapshot stale.
3. Album actions accept only the current revision. A stale handoff must explicitly offer “generate new image / share older image / cancel” and cannot reuse the snapshot silently.
4. Add a request sequence to asynchronous Canvas generation so an older completion cannot overwrite newer content.
5. Introduce a shared `CardSnapshot` so desktop and MiniTool at least share inputs, dimensions, and algorithm version.

Evidence: after changing a score, cover, clearing seeded content, or switching ratio, the old preview cannot be silently saved to the album; sharing requires the explicit three-way choice.

Current implementation: `src/minitool/renderRevision.ts` provides a deterministic content fingerprint; MiniTool previews record the revision that generated them; stale PNGs cannot be saved to the album or handed to Xiaohongshu; asynchronous generation cannot overwrite newer content. Focused tests, TypeScript checking, and the production MiniTool build pass.

### M1: Confirmation persistence and idempotent recovery

1. Upgrade the pending-post schema to v2 with `requestId`, `renderRevision`, target, confirmed text, image summary, creation time, and state.
2. Debounce-save title, body, tags, and signature edits on the confirmation page; restore the last confirmed content after `pagehide`, `visibilitychange`, or refresh.
3. Save the workspace and pending request before submission; a storage failure blocks the Bridge call.
4. After `accepted`, remove the actionable pending payload and keep a non-retryable local handoff record.
5. Recovery shows “handoff accepted” or “confirmation recoverable” and never invokes the platform automatically.
6. Add “discard this confirmation” to remove the pending payload without deleting the rating draft.

Evidence: confirmation edits survive a forced refresh; an accepted request does not invoke `postNote` again after refresh; cancellation permits editing and creates a new `requestId` on retry.

Current implementation: `postNoteStorage.ts` now uses Schema v2 with `requestId`, `renderRevision`, target, timestamps, and handoff state. Confirmation text is debounce-persisted after edits; workspace and the pending request are saved before the Bridge call; an `accepted` record remains non-retryable and only restores an informational state; “Discard this confirmation” clears the pending record without clearing the rating draft. Focused tests, TypeScript checking, and the production MiniTool build pass.

### M2: Capability and failure taxonomy

1. Use the shared result set: `completed`, `accepted`, `cancelled`, `denied`, `failed`, `unavailable`, `unknown`.
2. Map Bridge errors to permission denial, user cancellation, temp-file failure, album-write failure, and post-call failure.
3. When the Bridge is unavailable, disable actions that cannot run and keep a local PNG fallback visible.
4. Make desktop export distinguish success, user cancellation, and write failure; add a capability-probed system-share path in the browser.
5. Keep platform adapters narrow; the business layer depends on `ShareRequest`, `ShareResult`, and recovery records.

Evidence: every result has distinct copy and a usable next action; without a Bridge, editing, preview, and PNG export still work.

Current implementation: `minitoolBridge.ts` now returns the shared result vocabulary `completed/accepted/cancelled/denied/failed/unavailable/unknown`. Temporary-file failures, album-write failures, permission denial, missing Bridge, and opaque exceptions are classified separately; MiniTool provides dedicated recovery copy for album and posting outcomes. Bridge tests cover denial, cancellation, unavailability, failure, and unknown exceptions.

### M3: Signature and output consistency

1. Add `Personal signature (optional)` to local drafts, Archive Schema, and the confirmation page.
2. Empty values consume no card layout and have no scoring effect; non-empty values use safe length limits.
3. Desktop cards, MiniTool Canvas, PNG, album output, and post body use the same confirmed value.
4. Build 11-ratio preview/export/album input fixtures covering long titles, long signatures, no cover, cover, empty story, and many axes.
5. Record font loading, Canvas generation, and system-share return information without storing account tokens.

Evidence: signature placement is consistent across outputs; clearing it leaves no placeholder or old text.

Current implementation: the rating draft, Archive Schema, desktop editor, desktop card footer, MiniTool Canvas, PNG, and Xiaohongshu confirmation body now support an optional personal signature. Empty values occupy no layout space; non-empty values are limited to 120 characters and participate in the render revision. Desktop and MiniTool production builds plus the full unit suite pass.

### M4: Release acceptance and package handoff

1. Run focused unit tests, desktop E2E, MiniTool Bridge E2E, and the 11-ratio visual matrix.
2. On real devices, test first grant, denial, re-grant, cancellation, cache cleanup, and return recovery for album access.
3. Verify one-call Xiaohongshu `postNote`, accepted-then-refresh, cancelled retry, and failed retry.
4. Verify desktop export cancellation, unavailable system share, browser refresh, and download failure.
5. Produce bilingual change notes, test summary, package hashes, and known platform boundaries for the v0.4.0 candidate gate.

## 5. Suggested data structures

```ts
interface CardSnapshot {
  renderRevision: string;
  ratio: CardRatio;
  width: number;
  height: number;
  pngDataUri: string;
  algorithm: 'music-linear-100-v4';
  generatedAt: string;
}

interface PendingShareRequest {
  requestId: string;
  source: 'desktop' | 'web' | 'minitool' | 'toy' | 'wechat';
  target: ShareTarget;
  snapshot: CardSnapshot;
  text: { title?: string; content?: string; tags?: string; personalSignature?: string };
  state: 'confirming' | 'persisted' | 'invoking' | 'accepted' | 'cancelled' | 'failed';
  updatedAt: string;
}
```

## 6. Test matrix

| Category    | Scenario                                               | Expected result                                                              |
| ----------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Snapshot    | Change score, reason, cover, or ratio after generation | Old PNG is stale and cannot be saved or posted                               |
| Clear       | Clear seeded content after generation                  | Preview, post draft, and album action use a new empty revision               |
| Recovery    | Refresh, hide, or recover after confirmation edits     | Latest confirmed text and image are restored                                 |
| Idempotency | Refresh after accepted; click submit twice             | No automatic duplicate call; each retry is explicit and has a new request ID |
| Permissions | First denial, re-grant, native cancellation            | Denied, completed, and cancelled remain distinct                             |
| Capability  | No Bridge or no system share                           | Local editing and PNG export remain usable                                   |
| Output      | 11 ratios with signature on and off                    | Preview, PNG, album, and handoff inputs match                                |

## 7. Definition of done

- P0 gaps G1, G2, and G3 are closed.
- P1 gaps G4, G5, G6, and G7 have code and automated evidence; G8 has a visual gate or an explicitly accepted difference record.
- `ShareRequest`, `ShareResult`, pending schema, and error mapping match across English/Chinese docs, implementation, and tests.
- Platform copy never labels `accepted` as public and never labels system share as a completed platform post.
- The v0.4.0 candidate supports editing, preview, and local PNG export without a Bridge.
