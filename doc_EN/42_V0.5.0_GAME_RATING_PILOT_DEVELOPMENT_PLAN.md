# V0.5.0 Game-Rating Pilot Development Plan

Status: planning baseline; follows v0.4.0 sharing completion and does not start the standalone App

Date: 2026-09-25

## 1. Objective

The 0.5.0 pilot validates “domain pack + shared rating engine + rating card + sharing flow” with a minimal game domain. It is not a game database and not a one-shot frontend rewrite. The music mainline, Archive Schema, PNG export, and validated sharing state machine remain shared.

The pilot intentionally includes a small set of game templates with covers and personal ratings. Users can start from these examples and continue editing, but the examples must be presented as personal opinions and engineering fixtures—not official ratings, a leaderboard, or objective recommendations.

## 2. Product boundaries

### Required

- An independent game domain pack and entry point that does not replace the music entry.
- Game fields for title, platform, version/release information, cover, and optional notes.
- Game defaults, reasons, optional deductions, and aggregate-score rules through shared contracts.
- Three to five `Example template / personal rating` entries with scores, reasons, overall review, and a copyable template structure.
- Apply, copy as new, rename, and delete; editing a user copy must never mutate a seeded example.
- v0.4.x snapshot parity across preview, PNG, album save, signature, and sharing confirmation.
- Bilingual copy, narrow touch layout, keyboard use, empty states, and local draft recovery.
- Game Archive Schema migration, import/export, and regression fixtures.

### Explicitly out of scope

- Game databases, online metadata, leaderboards, comments, or account systems.
- Presenting personal templates as official recommendations or public rankings.
- Shipping commercial covers without clear usage rights in a public Toy, MiniTool, or release package.
- Duplicating the rating engine or silently changing historical music results.
- Android/iOS standalone App work; that remains v2.0.0.

## 3. Personal-rating template design

### 3.1 Template sources

| Source | Meaning | Deletable | Overwritable |
| --- | --- | --- | --- |
| `seeded-example` | Author examples shipped with the pilot | Yes | No; apply/copy into a user template |
| `user-created` | A template created from an example or blank entry | Yes | Yes |

Each template stores a stable ID, display name, source, created/updated timestamps, and a content snapshot. Renaming a seeded template must not turn its ID into mutable seed data.

### 3.2 Presentation and copy

- Every seeded card shows `Example template / personal rating`.
- Scores identify the author as a personal record; avoid “recommended,” “best,” or ranking language.
- Cover provenance and usage notes are discoverable from the template card.
- Clear-all affects the current work only and never deletes the template library.
- Empty-state copy states that scores, reasons, and gray placeholders are not real review content.

### 3.3 First-template coverage

The first three to five templates should cover long titles, different platforms, version differences, long reasons, extreme score distributions, landscape/portrait covers, and a no-cover fallback. The exact titles must be approved before implementation so examples are not mistaken for a product position.

## 4. Data and domain contract

Use a declarative domain pack instead of hard-coding a game branch in components:

```ts
interface GameTemplateDefinition {
  id: string;
  source: 'seeded-example' | 'user-created';
  title: string;
  cover?: LocalCoverRef;
  work: { platform?: string; version?: string; releaseNote?: string };
  axes: RatingAxis[];
  deductions: Deduction[];
  narrative?: string;
  personalSignature?: string;
  attribution?: { label: string; usage: 'cleared' | 'local-only' | 'unknown' };
}
```

Constraints:

1. Persist `source`, `id`, and `attribution` for audit and migration.
2. `seeded-example` content enters editing only through apply/copy.
3. Scoring rules, card layouts, and sharing orchestration depend on shared interfaces, not game names.
4. JSON export keeps the domain ID and algorithm version; old music archives must not be misclassified as game archives.

## 5. Phases

| Phase | Work package | Primary output | Exit gate |
| --- | --- | --- | --- |
| M0 | Domain contract and sample inventory | `GameDomainDefinition`, field table, source/rights inventory | Domain pack does not alter music defaults; every sample has a disposition |
| M1 | Template library and editing | Seeded templates, apply/copy/rename/delete, clear isolation | User edits never mutate seeds; refresh restores state |
| M2 | Scoring and cards | Game axes, reasons/deductions, eleven-ratio cards and signature | Preview, PNG, album, and sharing use one snapshot |
| M3 | Import/export compatibility | Schema migration, JSON fixtures, error states | Music archives remain readable; game archives are identifiable; corrupt files do not overwrite work |
| M4 | Acceptance and pilot package | Unit, E2E, visual matrix, Toy/MiniTool pilot package | No overflow, external resources, or rights violations; personal-rating labels remain visible |

## 6. Test matrix

- Templates: seed, apply, copy, rename, delete, clear without deleting templates, refresh recovery.
- Isolation: user edits, export/import, and deletion never mutate the original `seeded-example` snapshot.
- Scoring: unrated axes, full/low scores, deductions, long reasons, and empty reasons.
- Cards: eleven ratios, landscape/portrait covers, no cover, long titles, platform/version fields, empty/non-empty signatures.
- Compatibility: music Schema v2, game archives, unknown domain versions, and corrupt JSON.
- Security: no remote covers, account reads, third-party requests, or unreviewed assets in the public package.
- Accessibility: named template actions, confirmations for delete/clear, 44px touch targets, and focus restoration.

## 7. Deliverables and exit criteria

Deliver:

1. Bilingual game-domain and template-data documentation.
2. A deletable, copyable example-template library.
3. Game-domain unit, E2E, visual, and migration fixtures.
4. Pilot package, manifest, SHA-256, and known limitations.
5. Release copy that explicitly says “personal rating; not an official conclusion.”

Exit only when:

- The game domain can be enabled/disabled independently and music results remain unchanged.
- Seeded examples and user content are isolated, with verifiable delete/rename behavior.
- Eleven ratios and the sharing flow introduce no new stale-snapshot or overflow regressions.
- Every public cover has a recorded provenance decision.
- Domain evidence passes before the independent anime experiment starts in 1.0.0; the pilot must not grow into a game catalog.

## 8. Branch and order

```text
codex/v0.5.0-game-rating
  ├─ M0 domain contract and asset inventory
  ├─ M1 template library and isolation
  ├─ M2 rating cards and sharing reuse
  ├─ M3 archive migration
  └─ M4 pilot package and acceptance
```

Start with M0 and M1, then approve the exact template titles. Do not collect a large cover set before rights and data-isolation rules are fixed.
