# V0.3.1 Xiaohongshu Post Publishing Integration Plan

## 1. Decision and objective

The product owner has approved an explicitly user-triggered `window.xhs.miniTool.postNote` integration for **v0.3.1**. The released or acceptance-stage v0.3.0 remains immutable and continues to provide local editing, rating-card PNG generation, and album save only.

v0.3.1 lets a user enter Xiaohongshu's native posting flow after clearly confirming the exact images and text that will be submitted. The MiniTool must never publish in the background or report a native handoff as proof that a post is publicly published.

## 2. Scope

### Required

- Reuse the production rating-card model and all eleven ratios, using completed PNG data URIs as image resources.
- Provide a dedicated confirmation screen showing the title, body, tags, and every image to be submitted.
- Call `postNote` only after the user's final explicit action.
- Persist the recent draft and current posting parameters before native navigation so the flow is recoverable.
- Enforce a 20-Unicode-character title, 1,000-Unicode-character body, and 1–18 images.
- Distinguish “entered Xiaohongshu posting flow,” user cancellation, and retryable invocation failure; never claim the post was published.
- Preserve the offline ZIP, zero-backend, zero-telemetry, and Chrome 61 / ES2017 baselines.
- Ship Chinese and English UI, keyboard operation, screen-reader names, focus restoration, and safe-area adaptation together.

### Out of scope

- Completing the final public-post action on the user's behalf.
- Reading the user's Xiaohongshu account, posts, likes, or comments.
- Uploading to an application server or producing remote image URLs.
- Adding unconfirmed topics, locations, mentions, or marketing copy.
- Claiming that the Bridge returns a post ID or public publication state.

## 3. User flow

1. The user finishes rating and generates the production rating-card PNG.
2. The user chooses “Post to Xiaohongshu.”
3. A confirmation screen opens. It may prefill the work title and derive body text from the overall review and personal story; every field remains editable.
4. The screen continuously shows character counts, truncation notices, image count, and the privacy explanation.
5. The user selects “Continue to Xiaohongshu.” The app first saves the recent draft and pending post parameters, then invokes `postNote` once.
6. Bridge acceptance is reported as “entered Xiaohongshu posting flow.” Cancellation returns to the confirmation screen with content intact. Failure retains content and offers an explicit retry.
7. On returning to the MiniTool, the user may continue editing, regenerate the image, or initiate another post attempt.

## 4. Exported core algorithm

The pure algorithm lives in `src/minitool/postNotePayload.ts` and exports:

- `POST_NOTE_LIMITS`, the single source of truth for title, body, and image limits;
- `PostNoteDraft`, the UI input contract;
- `MiniToolPostNotePayload`, the serializable native Bridge argument;
- `BuildPostNotePayloadResult`, an explicit success-or-failure result;
- `isPostNotePngDataUri()`, complete PNG data-URI validation; and
- `buildPostNotePayload()`, which omits all-whitespace optional values, preserves other text exactly, truncates safely by Unicode code point, validates 1–18 images, and creates a fixed `photo_publish` argument.

The module has no dependency on the DOM, React, storage, or JSBridge and never publishes anything. The UI may safely call it before final confirmation and expose its `truncation` result. The Bridge adapter may accept only payloads that have passed this algorithm.

## 5. Module boundaries

| Module               | Responsibility                                                      | Must not                                   |
| -------------------- | ------------------------------------------------------------------- | ------------------------------------------ |
| `postNotePayload.ts` | Limits, validation, deterministic construction                      | Call the Bridge, mutate storage, render UI |
| `minitoolBridge.ts`  | Capability detection, one native call, cancellation/failure mapping | Compose product copy or retry silently     |
| Confirmation UI      | Prefill, edit, preview, explicit consent, status                    | Bypass validation or invoke automatically  |
| Local storage        | Preserve recent draft and pending parameters                        | Store a fabricated “published” state       |

Album save and post publishing must be detected independently. A device may support either capability without the other, so the existing pair of album functions cannot be a prerequisite for `postNote`.

| Milestone                   | Work                                                                        | Exit criteria                                                        |

On 2026-09-06, the product owner chose to skip a separate M3 stage and proceed directly to M4. This removes only the standalone milestone and intermediate package; it waives no quality gate. Production-card integration, eleven-ratio byte parity, screen-reader behavior, focus, and fallback paths are absorbed into M4 acceptance.

## 7. Acceptance gates

- `postNote` appears only in the synchronous chain of one explicit click.
- Missing images, more than 18 images, or any invalid image block the call with actionable feedback.
- Submitted title/body exactly match the confirmation screen; any automatic truncation is visible before the final click.
- Native cancellation is not an error, loses no draft, and never retries in a loop.
- If the Bridge is unavailable, PNG generation and album save remain usable and no false success state appears.
- Local editing submits no text or image to Xiaohongshu. The confirmation screen states that the final action hands the shown data to Xiaohongshu.
- The final ZIP still passes root `index.html`, classic-script, relative-path, CSP/network-string, size, and byte-parity audits.
- Automated acceptance never replaces exact-candidate real-device tests for posting, cancellation, return, and failure.

## 8. Version and release policy

- Do not modify, repack, or reuse hashes from v0.3.0 RC or released artifacts.
- v0.3.1 receives a new ZIP name, version identifier, manifest, SHA-256, and device record.
- Until every M4 gate passes, UI and documentation describe the build as an engineering candidate, not an accepted public-posting loop.
