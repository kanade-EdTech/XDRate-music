# V0.3.1 Bili Toy Current-Version Adaptation Plan

Status: Priority plan; adapt the current v0.3.1 rating and offline capabilities into a Bili Toy before starting v0.4.0 standalone mobile App work

Date: 2026-09-18

## 1. Objective and version relationship

This plan adapts the existing multidimensional music rating, eleven-ratio cards, templates, draft recovery, and PNG generation into an offline Web package uploadable to Bilibili Toy. The first Bili Toy only validates “open Toy → edit locally → preview → render PNG.” It adds no new domain rules and does not import Xiaohongshu-only JSBridge, `postNote`, or native-mobile capabilities.

Bili Toy is an adaptation work package for the current version. It does not replace v0.3.1 Xiaohongshu MiniTool and does not change the v0.4.0 standalone-mobile direction:

```text
Current v0.3.1 rating core
  ├─ Bili Toy adaptation candidate (this plan, priority)
  ├─ Xiaohongshu MiniTool (separate container and Bridge gates)
  └─ v0.4.0 standalone mobile App (later)
```

## 2. Initial scope

### Required

- A dedicated Bili Toy build entry and output directory that never overwrites the Xiaohongshu ZIP or desktop artifacts.
- An uploadable directory or ZIP with one unambiguous `index.html` entry.
- Relative runtime resources for the `/toy/<slug>/` subpath; no origin-root paths, remote fonts, or external CDN.
- Reuse of `music-linear-100-v4`, Archive Schema v2, all eleven ratios, and the shared preview/PNG rendering path.
- Drafts, content templates, and user-selected covers remain local to the current runtime; no Bilibili cloud storage, leaderboard, or telemetry in the first version.
- Chinese/English UI, narrow responsive layout, keyboard use, and the basic screen-reader flow remain usable.
- `toy_doctor.py` content preflight, independent build audit, and Bili Toy preview-page inspection before publishing.

### Explicitly out of scope

- Do not copy Xiaohongshu `window.xhs.miniTool`, `writeTempFile`, `saveImageToPhotosAlbum`, or `postNote` into Bili Toy.
- Do not add Bilibili account login, cloud sync, public publishing, leaderboards, or third-party requests.
- Do not treat Bili Toy as an Android/iOS native app; native mobile capability remains v0.4.0 work.
- Do not submit Toy review without explicit user confirmation, bind a video automatically, or change an existing Toy slug.

## 3. Toy platform constraints

The page runs under `/toy/<slug>/`, so it must satisfy:

- Use a relative build base such as `./`; HTML, CSS, and runtime resources must not use `/assets/...` origin-root paths.
- Use a single-page or hash route in the first version; do not depend on history fallback that the Toy server may not provide.
- Upload build output, not source, `.git`, `node_modules`, test reports, source maps, or local configuration.
- Keep one unambiguous `index.html` at the ZIP root or within exactly one top-level directory.
- Local covers are input and PNG content, not remote assets packaged into the Toy.
- If cloud storage or leaderboards are ever added, create a separate work package and review shared quotas, batching, event-based writes, and backoff; the first version has none.

The final URL is determined by the CLI preview and review result. Share with `index.html` in the Toy URL and do not promise immediate visibility after submission.

## 5. Dependencies and order

```text
Current v0.3.1 baseline
  └─ M0 prerequisites and boundaries (BTY-M0-01–04)
       └─ M1 Bili Toy shell and music loop (BTY-M1-01–04)
            └─ M2 package preflight and preview (BTY-M2-01–04)
                 └─ User confirmation, then review submission
                      └─ M3 online smoke and release copy (BTY-M3-01–02)
```

- Do not run a Toy write command before `BTY-M0-01` is complete.
- M1 may run in parallel with M0-02, but no Xiaohongshu Bridge code may enter the Bili Toy dependency graph.
- An M2 ERROR must be fixed before a new candidate is uploaded; do not upload a known blank or 404 package.
- A successful preview is not review approval. Fix a rejection and resubmit without deleting/recreating merely to change the slug.

## 6. Local commands and CLI gates

Command arguments and metadata fields must come from the installed `toy --help-json`, `toy create --help-json`, or `toy update --help-json`; do not hard-code flags from an old script or memory.

Standard flow:

1. Check that `toy` is installed; if missing, follow the official installation guidance rather than faking a CLI inside the repository.
2. Read the command tree and write markers to confirm the installed version supports the intended operation.
3. Build, audit, and run `toy_doctor.py`; resolve every ERROR first.
4. For a first publish or update, run `create` or `update` in JSON preview mode without `--yes`.
5. Give the returned `preview_url` to the user unchanged, with the target Toy, slug, changes, and an explicit “about to submit for review” notice.
6. Only after the user explicitly replies “submit for review,” rerun with exactly the same arguments and `--yes`.
7. Record the returned `id`, `status`, `preview_url`, source commit, package hash, and known limitations.

The official `toy v0.5.0` is installed and verified, but OAuth login is not complete; only local builds and static preflight are allowed until login is confirmed, and no Toy write command may run.

## 7. Candidate and version policy

- Adaptation branch: `codex/bili-toy-v0.3.1`.
- Local probe: `0.3.1-toy-alpha.1`, never submitted for review.
- First preview package: `0.3.1-toy-rc.1`, preview only and no `--yes`.
- Submit only after explicit user confirmation and a clean preview; fixes use `rc.2` or later and never overwrite old packages or reuse hashes.
- Bili Toy id, slug, cover, and metadata are independent from Xiaohongshu MiniTool; updates retain the existing slug.
- The current v0.3.1 algorithm, Archive Schema, PNG cards, and Web behavior must not silently change for Toy adaptation.
