# V0.3.1 M4 Device Acceptance and Release Plan

Status: Pending execution; RC.1 is frozen, while real-container, device, permission, and screen-reader gates still block public release

Date: 2026-09-07

## 1. Objective and boundary

This plan moves v0.3.1 M4 from an engineering candidate that passed automation and static audit to a device candidate on which a release decision can be made. Acceptance covers only user-triggered rating-card generation, album save, and the explicit-confirmation handoff of images and text to Xiaohongshu's native posting flow.

This round does not promise background or automatic posting, proof of public publication, photo-library reading, remote services, accounts, or compatibility with unrecorded platform versions. An accepted `postNote` result means entry into the native posting flow only.

## 5. Evidence management

Store raw evidence under a Git-ignored directory such as:

```text
artifacts/minitool/v0.3.1-rc.1-acceptance/
  pc-simulator/
  android-8.1/
  android-current/
  ios-18.4-plus/
```

Name files as `platform_caseID_date_sequence`, for example `android-current_POST-02_20260907_01.mp4`. Repository documents should contain sanitized conclusions and necessary hashes only. Do not commit account details, avatars, device serials, notifications, private photos, or unlicensed works.

## 6. Roles and handoff

- Test operator: install the same RC.1 on real devices, execute cases, and retain raw evidence.
- Engineering: reproduce and classify failures and maintain fixes, automation, candidates, and change records.
- Release owner: review the matrix, privacy boundary, and known limitations, then decide to release, fix and retest, or stop.

Every finding records platform, case ID, reproduction steps, expected and actual behavior, frequency, evidence file, and blocking status. “Has a problem” or “looks fine” is not sufficient evidence.

## 7. Failure and new-candidate policy

1. Any source, build-configuration, or ZIP-content change immediately removes RC.1 from release consideration.
2. Never patch or recompress RC.1 directly; commit the fix and add regression coverage.
3. Produce `v0.3.1-rc.2` or later with a new manifest and SHA-256, then restart from P0.
4. Shared logic, card, or Bridge changes require the full platform matrix. A platform-only fix must at least rerun the affected platform, with P5 deciding whether the complete matrix is required.
5. If a platform capability is genuinely absent, document affected versions and fallback behavior. Automated simulation cannot replace a device verdict.

## 8. Release definition of done

`V031-M4-01` may be completed and public release prepared only when all conditions hold:

- P0–P5 are complete and all four platform records have no blank fields;
- album allow/deny/cancel/recover and post accept/cancel/fail/return matrices pass;
- key TalkBack and VoiceOver flows have evidence;
- all eleven ratios avoid overflow and preview, save, and submission use the same rating-card image;
- no third-party request or undeclared Bridge capability is observed;
- release notes state that acceptance is not public publication and list actual known limitations;
- the uploaded ZIP matches this plan's frozen hash, or a new RC has fully replaced it in the documentation.

If any blocker remains open, the verdict stays “engineering candidate, eligible for continued testing, not for public release.”
