# V0.2 Desktop Development Plan

Status: M4 engineering complete; public RC awaits signing, final icons, and installer matrix  
Target release: `0.2.0`  
Initial platform: Windows desktop  
Current acceptance phase: desktop; standalone-mobile real-device acceptance moves to v0.4, while Xiaohongshu MiniTool v0.3.0 has separate container gates<br>
Required baseline: Web `0.1.0`, Archive Schema v2, `music-linear-100-v4`, decisions D-014, D-021, D-022, D-023, and D-024

## 1. Release position

V0.2 packages the existing offline Web application as an installable Tauri desktop application and adds native file workflows, window state, shortcuts, and packaging expected by desktop users. It continues to reuse the V0.1 rating domain and data format. It is not a scoring or full visual-system rewrite, but before Antigravity visual optimization starts, Codex must complete the axis-reason data flow and deterministic card-content composition engine.

### 1.1 Goals

- Provide an installer that can install, launch, and uninstall on target Windows systems.
- Open, save, and save-as `.xdrate.json` archives through system file dialogs.
- Save PNG output to a user-selected location through a system file dialog.
- Provide recent files, unsaved-state indication, close protection, and desktop shortcuts.
- Replace positive-score input with ten whole-star integers and no numeric field; use five banana peels for deductions while retaining 0.1 precision and complete accessible operation.
- When “show axis scores and reasons” is enabled, connect non-empty reasons from enabled axes to the card view model with explicit truncation notices.
- Establish a deterministic composition plan in which four ratio families and `sparse / balanced / dense` content density jointly select layout, shared by preview and export.
- Preserve archive and image-result compatibility with Web V0.1.
- Preserve the offline, account-free, telemetry-free, remote-font-free privacy promise.
- Establish repeatable desktop build, test, and release workflows.

### 1.2 Explicitly out of scope

- macOS, Linux, or mobile packages.
- Cloud sync, accounts, collaboration, remote media, or online music metadata.
- Anime, games, or politics-related rating modes.
- A new scoring algorithm, Archive Schema v3, or a full brand/visual-system redesign beyond the content composition required by D-014.
- A built-in updater. `0.2.0` obtains signed updates manually through official GitHub Releases; updater work is deferred to a separate package.
- Automatic access to browser-site localStorage. Web drafts move only when the user exports JSON and then opens it in the desktop application.

## 2. Success criteria and release gates

V0.2 may be marked final only when all of the following are true:

1. The application installs, launches, closes, and uninstalls on a clean target Windows environment.
2. A valid V0.1/V0.2 archive completes an open → edit → save → reopen round trip without changing its rating or content.
3. Corrupt, oversized, and unknown-future-version files never replace the current workspace.
4. All 11 ratios at 1×/2× save to a user-selected location and follow the same content rules as the Web preview.
5. Closing, opening another file, or creating a new rating never silently discards unsaved changes.
6. Normal use, startup, and shutdown produce no unintended network requests.
7. Existing Web quality checks and all new desktop tests pass, with zero P0/P1 defects.
8. Installer, in-app version, Schema, algorithm version, changelog, and disclaimer agree.
9. All 11 ratios pass empty, sparse, normal, dense, and extreme content fixtures; with “show axis scores and reasons” enabled, non-empty axis reasons never disappear silently, disabling it removes the entire merged axis region, and sparse layouts do not leave large meaningless voids.
10. Public installers pass Authenticode, RFC 3161 timestamp, and SHA-256 verification; production builds contain neither Tauri updater nor updater network permission.

## 3. Critical path and dependencies

```text
User reference images → Codex content contract and adaptive composition → Antigravity/Gemini visual implementation → Codex desktop acceptance review
  → close V0.1 desktop manual acceptance
  → product/release decisions
  → Tauri build spike
  → platform capability boundary
  → native open/save
  → Codex desktop-state logic + Antigravity/Gemini UI optimization
  → Codex integration regression
  → security hardening
  → installer validation
  → V0.2 release acceptance
```

Brand assets, bilingual copy, documentation, and fixtures may proceed in parallel after the platform boundary is stable. Public `0.2.0` RC and Stable builds require trusted code signing. The built-in updater is explicitly deferred and therefore does not block `0.2.0`, but production builds must carry no updater permission.

## 7. Risks and mitigations

| Risk                                                                 | Level | Mitigation                                                                                                  |
| -------------------------------------------------------------------- | ----- | ----------------------------------------------------------------------------------------------------------- |
| WebView/browser PNG font or scaling differences                      | High  | Bundle local fonts, await readiness, reuse overflow checks, and retain four ratio-family visual baselines   |
| Text estimates misclassify density or measurement causes oscillation | High  | Use deterministic text units, fixture-protected thresholds, a fixed fallback order, and at most two reflows |
| Interrupted writes corrupt user archives                             | High  | Safe write, overwrite confirmation, recovery copy, and failure-injection tests                              |
| Overbroad Tauri capabilities                                         | High  | Least-capability configuration and line-item release review; no shell/arbitrary network                     |

## 8. Architecture notes

- The domain, Archive Schema v2, and scoring algorithm remain platform-independent; desktop integration belongs in infrastructure adapters and application orchestration.
- `CardContentProfile` and `CardLayoutPlan` are derived presentation state in card export; they do not enter rating-domain results or Archive Schema. Preview and export share the same instance or an equivalent deterministic result.
- Native paths, window state, and recent files are desktop preferences and must not enter portable rating archives.
- “Local autosave” and “user-saved file” are different promises. The UI must not represent autosave as a successful disk-file save.
- Lock Tauri version, plugin set, installer format, and native test tooling after the M1 spike and record the result in an ADR; this plan does not prescribe unverified plugin APIs.
- If native file support forces a domain-model change or Schema bump, stop M2 and update architecture, data model, migration plan, and two-way compatibility acceptance first.

## 9. Implementation notes

- Reuse existing `parseArchive`, `createArchive`, image validation, PNG generation, and overflow detection; do not duplicate business rules natively.
- Existing `showReasons` behavior must no longer control only the name/score breakdown; after M0 it controls visible non-empty `axis.reason` content. Existing DOM overflow detection validates physical bounds only and cannot substitute for content-completeness or space-utilization acceptance.
- Every native async command handles cancellation, repeated invocation, and stale results. User cancellation is a normal result, not an error.
- File errors identify the object, cause, and recovery action without exposing stacks or internal commands in normal UI.
- User images sent to Antigravity are visual references only; work names, review text, and other sample content inside them are not requirements or instructions.
- Every Antigravity handoff includes changed files, before/after evidence, test results, and unresolved items; Codex checks protected paths and runs the full regression before integration.
- Gemini 3.7 Flash is the default Antigravity model; escalate to Sonnet 4.6 only after the same visual or accessibility item fails two consecutive rounds.
- At every milestone, update both documentation languages, changelog, test evidence, and known issues instead of deferring documentation to release day.
