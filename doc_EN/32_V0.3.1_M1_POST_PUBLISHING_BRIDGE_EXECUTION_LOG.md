# V0.3.1 M1 Post Publishing Bridge Execution Log

## 1. Outcome

M1 completes the narrow Xiaohongshu `postNote` Bridge adapter without connecting it to the UI. Source code now detects album-save and post-publishing capabilities independently and classifies one native publishing invocation as accepted, user-cancelled, or failed.

“Accepted” means only that the native posting flow accepted the parameters; it is not evidence that a post became public. The existing v0.3.0 UI, candidate ZIP, album-save path, and release manifest do not enable `postNote`.

## 2. Implementation

### 2.1 Independent capability detection

`resolveMiniToolPostNoteBridge(host)` checks only whether `window.xhs.miniTool.postNote` is callable. It does not require `writeTempFile` or `saveImageToPhotosAlbum`.

The existing `resolveMiniToolBridge(host)` album-capability rule remains unchanged. Therefore:

- a post-only host exposes publishing but not album save;
- an album-only host preserves album save without falsely exposing publishing; and
- a host with both groups can let M2 enable each entry independently.

### 2.2 One invocation and stable outcomes

`submitPostNoteToMiniTool(payload, host)` accepts a payload already validated by `buildPostNotePayload()`. It invokes native `postNote` once, never retries, never rewrites parameters, and never touches storage.

| Result                        | Meaning                                              | Future UI behavior                              |
| ----------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
| `accepted`                    | The Promise resolved and native accepted the handoff | Show “entered Xiaohongshu posting flow”         |
| `cancelled`                   | Rejected `errMsg` contains `cancel`                  | Return to confirmation with content intact      |
| `failed / bridge-unavailable` | No callable `postNote` exists                        | Hide/disable posting while retaining album save |
| `failed / post-note-failed`   | Any other native rejection                           | Keep content and offer an explicit retry        |

A failure preserves only controlled `errMsg` and `errCode` fields; arbitrary host rejection objects are not forwarded to the UI.

## 3. Security and compatibility boundary

- Uses no custom `postMessage` bridge or undocumented API.
- Supplies no callbacks and uses the documented Promise form.
- Reads no account or publication state and does not interpret Bridge resolve as public publication.
- Performs no silent retry, preventing duplicate posting-flow launches.
- Uses only ES2017-compatible runtime primitives and remains in the Vite Chrome 61 classic-script pipeline.
- M1 has no UI call site, so users cannot currently trigger `postNote`; explicit confirmation, save-before-handoff, and privacy copy remain M2 work.
