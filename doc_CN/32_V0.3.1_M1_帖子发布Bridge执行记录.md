# V0.3.1 M1 帖子发布 Bridge 执行记录

## 1. 结论

M1 已完成小红书 `postNote` 窄 Bridge 适配，但尚未接入用户界面。源码能够独立判断相册保存能力和帖子发布能力，并把一次原生发布调用归类为“已受理”“用户取消”或“调用失败”。

“已受理”只表示原生发帖流程接受了参数，不代表帖子已经公开发布。v0.3.0 的现有界面、候选 ZIP、相册保存链路和发布清单均未启用 `postNote`。

## 2. 实现内容

### 2.1 独立能力探测

`resolveMiniToolPostNoteBridge(host)` 只检查 `window.xhs.miniTool.postNote` 是否为可调用函数，不要求 `writeTempFile` 或 `saveImageToPhotosAlbum` 存在。

原 `resolveMiniToolBridge(host)` 的相册能力判定保持不变。因此：

- 只有 `postNote` 时，可以识别发布能力，但不能识别相册能力；
- 只有相册两个函数时，可以继续保存相册，但不会误报发布能力；
- 两组能力同时存在时，后续 M2 可以分别启用对应入口。

### 2.2 单次调用和结果模型

`submitPostNoteToMiniTool(payload, host)` 接收已经由 `buildPostNotePayload()` 验证的参数，只调用一次原生 `postNote`，不重试、不改写参数、不访问存储。

| 结果                          | 含义                               | 后续 UI 行为                 |
| ----------------------------- | ---------------------------------- | ---------------------------- |
| `accepted`                    | Promise 已 resolve，原生流程已受理 | 显示“已进入小红书发布流程”   |
| `cancelled`                   | reject 的 `errMsg` 包含 `cancel`   | 回到确认页并保留内容         |
| `failed / bridge-unavailable` | 没有可调用的 `postNote`            | 隐藏或禁用入口，保留相册功能 |
| `failed / post-note-failed`   | 其他原生 reject                    | 保留内容并允许用户主动重试   |

失败结果仅保留受控的 `errMsg` 与 `errCode`，不会把任意宿主异常对象传给 UI。

## 3. 安全与兼容边界

- 不自行使用 `postMessage` 或任何未列入容器规范的 API。
- 不传回调字段，使用规范允许的 Promise 调用形式。
- 不读取账号或发布状态，不把 Bridge resolve 解释为公开发布。
- 不进行静默重试，防止重复打开发帖流程。
- 新代码只依赖 ES2017 可用能力，并继续由 Vite 输出 Chrome 61 兼容经典脚本。
- M1 没有 UI 调用点，用户当前无法触发 `postNote`；显式确认、草稿先保存和隐私文案留在 M2 实现。

## 4. 自动化覆盖

- 发布能力和相册能力的独立探测；
- 精确参数只调用一次；
- Bridge 不可用时不调用相册 API；
- 原生取消单独分类；
- 原生失败保留经过清理的 `errMsg` / `errCode`；
- 未知异常对象不泄漏到结果；
- 原相册保存成功、取消和失败回归。
