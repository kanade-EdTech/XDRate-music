# V0.4.0 旧版独立移动 App 计划（已撤回）

> 本文件保留历史规划，已不再作为当前开发入口。自 2026-09-22 起，v0.4.0 改为“分享机制完善”，独立 App 实体推迟至 v2.0.0。当前路线以[版本路线重排与后续开发计划](./39_版本路线重排与后续开发计划.md)为准。

状态：计划阶段；在 v0.3.1 M4 真机门禁完成后进入正式实施

日期：2026-09-07

## 1. 产品定位

v0.4.0 是独立移动 App 验证版，不是小红书小工具的移动扩展，也不是 1.0.0 多领域产品的提前发布。它使用现有音乐评分流程验证移动端产品形态，同时把只能服务音乐的实现逐步整理为可供动漫、书籍、影视等领域复用的评分内核。

v0.4.0 的成功标准不是“加入尽可能多的领域”，而是证明移动基础能力能在真实手机上稳定工作，并且不需要为每个领域复制一套算法、存档和卡片代码。

## 2. 目标

- 交付可安装、可离线运行的独立移动 App 候选，覆盖 Android 与 iOS 的真实设备验证。
- 复用 `music-linear-100-v4`、Archive Schema v2 和正式评分卡，不降低既有数据兼容性。
- 验证移动端安全区、软键盘、触控、屏幕旋转、后台恢复、系统分享、图片选择与相册保存。
- 建立与平台无关的领域定义模型，使轴、默认模板、作品字段、文案和卡片标签可由领域包配置。
- 使用音乐作为公开交互，使用动漫、书籍和影视作为内部契约夹具，证明核心没有音乐专属硬编码。
- 为 1.0.0 冻结多领域评分器所需的边界、迁移方案和真实设备证据。

## 3. 不在 v0.4.0 范围内

- 不公开承诺完整的动漫、书籍或影视评分产品体验。
- 不引入账号、云同步、后端、遥测或在线素材库。
- 不把小红书 `window.xhs.miniTool`、离线 ZIP 或 `postNote` 约束带入独立 App。
- 不在没有必要性证据时重写现有 React/TypeScript 领域逻辑。
- 不冻结 1.0.0 的最终领域列表、每个领域的评分轴或品牌视觉。

## 4. 技术路线与决策门禁

Tauri Mobile 作为原生 App 壳的首选验证方向，响应式 PWA 作为复用、性能与可访问性的对照基线。M0 必须用最小探针比较两者的安装、离线、文件/媒体、分享、生命周期、包体和无障碍表现，再冻结 v0.4.0 的交付壳。

只有出现关键插件不可用、性能或读屏不达标、系统交互无法可靠实现等可复现证据时，才评估 Flutter。若评估 Flutter，必须同时提交双栈维护成本、Archive 兼容方案、算法一致性测试和迁移计划，不能仅以“更原生”为理由重写。

建议平台边界：

```text
Rating domain core
  ├─ DomainDefinition / preset packs
  ├─ scoring + archive migration + card view model
  └─ PlatformServices
       ├─ Web
       ├─ Windows desktop
       ├─ Xiaohongshu MiniTool
       └─ Standalone mobile App
```

领域包只能提供声明式配置和经过验证的规则，不得直接调用移动、桌面或小工具 API。

## 7. 依赖顺序与并行边界

```text
v0.3.1 M4 真机收口
  └─ M0-01 / M0-02 / M0-03（可并行）
       └─ M0-04 壳层 ADR
            ├─ M1 移动纵向闭环
            └─ M3-01 领域契约设计
                 └─ M2 原生媒体与数据 + M3-02～05 内核验证
                      └─ M4 真机候选与 1.0.0 交接
```

- M0-04 未通过前，不大规模接入移动插件或修改正式领域模型。
- M1 与 M3-01 可以在边界冻结后并行，但 M3 不得破坏音乐行为来迁就内部夹具。
- M2 的系统能力必须通过 `PlatformServices` 接入；权限实现不能绕过领域边界。
- M4 只验收来自干净提交的精确候选包；候选内容变化必须升序号并重跑受影响矩阵。

## 8. 多领域内核最小契约

v0.4.0 应验证但不急于公开的领域定义至少包含：

- 稳定 `domainId`、本地化名称和版本；
- 默认正向项、可选扣分规则和权重约束；
- 可配置作品字段，例如艺术家、作者、导演、出版社、播出年份；
- 领域默认模板与用户自定义模板的来源区分；
- 卡片品牌标题、字段顺序和可访问描述；
- 存档中的领域标识、定义版本和迁移入口；
- 未知领域、缺失领域包和旧存档的安全降级。

同一份输入必须在 Web、桌面、小工具和移动 App 的共享算法测试中得到一致结果。若未来领域需要不同评分区间或聚合规则，必须通过带版本的规则配置进入，不能在 UI 中硬编码分支。

## 9. 真实设备矩阵

最低验收范围：

- 一台仍在支持范围内的较旧 Android 设备；
- 一台当前 Android 设备；
- 一台 iOS 当前主版本设备；
- TalkBack 与 VoiceOver；
- 竖屏、横屏、软键盘、前后台切换、低存储和权限拒绝/恢复；
- 无网首次启动与正常使用；
- 中文、英文和长文本评分卡；
- Archive 从现有版本导入以及导出后回读。

具体最低系统版本必须由 M0 探针结果决定，不能在没有真机证据时写入公开兼容承诺。

## 10. 通往 1.0.0 的交付物

v0.4.0 完成时必须为 1.0.0 留下：

1. 已验证的独立移动 App 壳和平台服务契约；
2. 至少四类领域夹具共用的领域定义与评分接口；
3. Archive Schema v2 的兼容结论，以及是否需要 Schema v3 的书面决策；
4. 音乐存档无损迁移和跨平台算法一致性测试；
5. 动漫、书籍、影视领域的研究清单，而不是未经验证的默认轴；
6. Android/iOS 性能、无障碍、权限和失败恢复基线；
7. 1.0.0 产品范围、领域名单和版本迁移风险清单。

## 11. 1.0.0 初步定位

1.0.0 定位为 `XDRate` 多领域评分器，首要候选领域包括音乐、动漫、书籍和影视，其他领域须经独立研究和产品确认后加入。用户可选择领域、使用领域预设或创建自定义评分结构，并生成统一品牌下的领域化评分卡。

1.0.0 进入开发前还需要单独确认：首发领域名单、各领域默认轴和扣分语义、通用版与垂直版关系、包名与升级路径、Schema v3 是否必要，以及 Web/桌面/移动端哪些属于首发平台。

## 12. 版本、分支与候选策略

- 正式实施使用短生命周期 `codex/v0.4.0-*` 功能分支；M0 探针合并前不得把实验依赖带入生产构建。
- 版本号、Tauri/移动清单和用户界面必须由同一版本检查门禁保持一致。
- M0/M1 产物只标记为开发探针或 `alpha`，不得公开称为移动版发布候选。
- M2/M3 合并且数据迁移门禁通过后才可生成 `0.4.0-beta.1`。
- M4 自动化、签名和精确真机矩阵准备完成后生成 `0.4.0-rc.1`；包内容变化使用 `rc.2` 等新序号，禁止覆盖旧候选。
- 0.4.0 不改变现有 v0.3.0/v0.3.1 小工具包，也不复用其应用标识、Bridge 或候选哈希。

## 13. 主要风险与回退

| 风险                       | 早期信号                           | 处理与回退                                                                            |
| -------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------- |
| iOS 构建或签名设备不足     | M0 无法在真实 iPhone 安装          | 保持 Android 探针可推进，但不降低 iOS 发布门禁；补齐 macOS/Xcode/账户后再冻结平台范围 |
| 原生插件权限过宽或维护不足 | 请求任意文件、网络或长期未维护依赖 | 自建窄适配器、选择更小能力插件或回退 PWA；不能以进度为由接受过宽权限                  |
| 大图导致内存峰值或崩溃     | 老设备选择高像素图片时退出         | 降采样、分阶段压缩、限制输入并提供可恢复提示；把峰值纳入设备门禁                      |
| 多领域抽取改变音乐结果     | 既有黄金夹具、PNG 或存档变化       | 立即阻止合并；先加兼容层，再以显式 ADR 和迁移处理必要变化                             |
| Schema v3 过早扩大范围     | M3 前出现大量迁移工作              | 默认保持 v2；只有领域标识无法向后兼容时才启动 v3 决策                                 |
| 移动 UI 与桌面代码互相污染 | 平台条件散落在领域组件             | 收紧平台契约和依赖检查，必要时拆入口而不复制领域逻辑                                  |

## 14. 估算与发布门禁

在工具链和测试设备可用的前提下，工程估算为 25–40 个有效开发日：M0 4–7 日、M1 6–9 日、M2 5–8 日、M3 6–10 日、M4 4–6 日。该估算不包含 Apple/Google 账户审核、证书采购、等待外部商店审核或设备采购时间。

0.4.0 只有在以下条件全部满足时才能发布：

- M0–M4 原子工作包关闭，且中英文文档、变更记录和用户说明同步；
- Android/iOS 精确候选、横竖屏、权限、生命周期和读屏矩阵通过；
- 现有音乐算法、Archive 和评分卡兼容门禁通过；
- 动漫、书籍、影视内部夹具证明共享内核可用，但未作为已完成产品宣传；
- 离线、最小权限、签名、哈希和供应链清单通过；
- 1.0.0 交接评审已记录仍需研究和确认的事项。
