# V0.3.1 Bili Toy 当前版本适配开发计划

状态：当前容器适配计划；交互修复基线为 v0.3.3。Bili Toy 完成后进入 v0.4.0 分享机制完善，不再直接进入独立移动 App。

日期：2026-09-18

## 1. 目标与版本关系

本计划把当前已经完成的多维音乐评分、11 种比例评分卡、模板、草稿恢复和 PNG 生成能力，适配为 B 站 Toy 可上传的离线 Web 包。第一版 Bili Toy 只验证“打开 Toy → 本地填写 → 预览 → 生成 PNG”的稳定性，不新增领域评分规则，也不把小红书专用 JSBridge、`postNote` 或移动 App 原生能力带入 Toy。

Bili Toy 是当前版本的发布适配工作包，不替代 v0.3.1 小红书小工具，也不改变 v0.4.0 的移动 App 方向：

```text
当前 v0.3.1 评分卡核心
  ├─ Bili Toy 适配候选（本计划，优先）
  ├─ Xiaohongshu MiniTool（独立容器和 Bridge 门禁）
  └─ v0.4.0 分享机制完善 → v1.0.0 多领域 → v1.1.0 微信小程序 → v2.0.0 独立 App 实体
```

## 2. 首版范围

### 必须交付

- Bili Toy 独立构建入口和独立输出目录，不覆盖小红书 ZIP 或桌面构建产物。
- 构建产物为可上传的目录或 ZIP，入口为唯一 `index.html`。
- 所有运行资源使用相对路径，适配 `/toy/<slug>/` 子路径；不依赖站点根路径、远程字体或外部 CDN。
- 复用当前 `music-linear-100-v4`、Archive Schema v2、11 种比例和同源预览/PNG 生成逻辑。
- 本地草稿、内容模板和用户主动选择的封面继续只在当前运行环境保存；首版不读取 B 站云存储、不做排行榜、不收集遥测。
- 中文/英文界面、窄屏响应式、键盘操作和基本读屏流程保持可用。
- 发布前经过 `toy_doctor.py` 内容预检、独立构建审计和 Bili Toy 预览页检查。
- 首屏提供“一键清除”：清除默认作品文字、评分、理由、故事和封面，但保留已保存模板、语言设置和页面结构。
- 清除后保留灰色占位说明，明确空白区域用途；占位文字不参与评分、不进入 PNG、不保存为作品内容。
- 修复专业模式默认数据：专业模式必须载入预设评价轴；只有自定义模式允许以空白评价轴开始。

### 明确不做

- 不把小红书 `window.xhs.miniTool`、`writeTempFile`、`saveImageToPhotosAlbum` 或 `postNote` 复制到 Bili Toy。
- 不新增 B 站账号登录、云同步、公开发布、排行榜或第三方网络请求。
- 不把 Bili Toy 当作 Android/iOS 原生 App；移动端原生能力仍属于 v0.4.0。
- 不在没有用户明确确认前提交 Toy 审核，不自动绑定视频，也不修改已有 Toy 的 slug。

## 3. Toy 平台硬约束

页面实际运行在 `/toy/<slug>/` 子路径下，因此必须满足：

- Vite 等构建工具使用相对 base（例如 `./`）；HTML、CSS 和运行时资源不得使用 `/assets/...` 根绝对路径。
- 首版使用单页或 hash 路由；不得依赖无法由 Toy 服务器提供的 history 路由回退。
- 上传构建产物，不上传源码、`.git`、`node_modules`、测试报告、source map 或本地配置。
- ZIP 根目录或恰好一个一级目录内只能有明确的 `index.html` 入口，不制造多个候选入口。
- 本地封面只作为页面输入和 PNG 内容，不作为 Toy 上传包内的远程素材。
- 若后续加入云存储或排行榜，必须另开工作包，按共享配额、批量读写、事件提交和退避重试规则评审；首版默认不加入。

最终发布地址必须以 CLI 预览和审核返回为准。对外分享使用带 `index.html` 的 Toy URL，不承诺提交后立即上线。

## 5. 依赖和执行顺序

```text
v0.3.1 当前基线
  └─ M0 前置与边界（BTY-M0-01～04）
       └─ M1 Bili Toy 页面与音乐主链（BTY-M1-01～04）
            └─ M2 包体预检与预览（BTY-M2-01～04）
                 └─ 用户确认后审核提交
                      └─ M3 线上 Smoke 与发布说明（BTY-M3-01～02）
```

- `BTY-M0-01` 未完成前不调用 Toy 写操作。
- M1 可以与 M0-02 并行，但任何小红书 Bridge 代码都不得进入 Bili Toy 构建依赖图。
- M2 发现 ERROR 必须修复后重新生成候选；不得上传一个已知白屏或 404 的包。
- 预览成功不等于审核通过；审核失败只按拒绝原因修复和重提，不删除重建来改变 slug。

## 6. 本地命令与 CLI 闸门

命令参数和元信息字段必须以本机 `toy --help-json`、`toy create --help-json` 或 `toy update --help-json` 为准，不把旧脚本或记忆中的 flag 写死到自动化中。

标准流程：

1. 检查 `toy` 是否安装；未安装时按官方安装说明处理，不在仓库内伪造 CLI。
2. 读取命令树和写入标记，确认当前版本支持目标操作。
3. 运行 Bili Toy 构建、审计和 `toy_doctor.py`，先解决所有 ERROR。
4. 首发或更新先调用 `create` / `update` 的 JSON 预览模式，不带 `--yes`。
5. 把返回的 `preview_url` 原样交给用户检查，并明确展示目标 Toy、slug、改动内容和“即将提交审核”。
6. 只有用户明确回复“提交审核”后，使用完全相同参数重跑并加 `--yes`。
7. 记录返回的 `id`、`status`、`preview_url`、源提交、包哈希和已知限制。

当前环境已安装并验证官方 `toy v0.5.0`，但 OAuth 登录仍未完成；因此当前只允许做本地构建和静态预检，禁止调用 Toy 写操作。

## 7. 发布候选与版本策略

- 适配开发分支：`codex/bili-toy-v0.3.1`。
- 本地探针：`0.3.1-toy-alpha.1`，不得上传审核。
- 首个可预览包：`0.3.1-toy-rc.1`，只执行预览，不带 `--yes`。
- 用户明确确认且预览无误后才提交审核；审核修复使用 `rc.2` 或更高序号，禁止覆盖旧包或复用旧哈希。
- Bili Toy 的 Toy id、slug、封面和元信息与 Xiaohongshu MiniTool 独立；更新已有 Toy 必须保留原 slug。
- 当前 v0.3.1 的评分算法、Archive Schema、PNG 卡片和 Web 行为不得因 Toy 容器适配而静默改变。

## 11. M1.1 交互修复要求

### 11.1 一键清除

在页面开头、评分摘要附近提供高可见度的“一键清除”按钮。点击后清除当前默认示例的作品名、艺术家、专辑、年份、封面、评价轴分数、评分理由、负面项、总体评价和个人故事；已保存模板、语言选择和应用结构不受影响。若当前内容已有用户修改，应先二次确认。

### 11.2 清除后的灰色占位说明文案

清除完成后保留空白布局，并显示以下提示：

> 已清除默认内容，当前是一张空白评分卡。灰色文字只是填写提示，用来说明这里可以填写什么；它不会计入评分，不会出现在导出的 PNG 中，也不会保存为作品内容。你可以从作品信息、评价轴、分数和评分理由开始填写；暂时留空也不会影响页面继续使用。

提示文案使用低对比度灰色无衬线字体，不能伪装成真实内容；用户开始输入后，对应占位提示自动消失。

### 11.3 专业模式默认值

当前 Toy 中“专业模式”不可表现为一片空白，也不能退化成“自定义模式”。首次切换到专业模式时，必须创建并显示专业预设评价轴：`填词 / 立意`、`作曲 / 编曲`、`演唱 / 调音 / 混音`、`创新`、`其他`。分数初始为未评分，权重和理由保持可编辑；只有用户主动选择“自定义模式”时才允许从空白评价轴开始。该行为覆盖新开页面、清除默认内容后切换、刷新恢复和模板应用。

### 11.4 回归证据

- 一键清除前后截图各一张，确认默认文本和评分被清除、灰色说明仍在。
- 专业模式首次进入截图，确认五个预设轴可见；自定义模式截图，确认空白起始仍可用。
- 导出 PNG 对照，确认灰色占位说明不进入卡片内容。
